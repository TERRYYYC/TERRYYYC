## 一、项目全貌 / Project Overview

**Cat Café** 是一个真实项目的完整复盘教程：构建一个让三只 AI（Claude Opus、GPT Codex、Gemini）在同一个系统中自主协作的 Web 应用。

| 猫咪 / Cat | 模型 | 角色 |
|---|---|---|
| 布偶猫 Ragdoll | Claude Opus | 主架构师、核心开发 |
| 缅因猫 Maine Coon | GPT Codex | 代码审查、安全、测试 |
| 暹罗猫 Siamese | Gemini | 视觉设计、创意颠覆 |

**核心痛点 / Core Problem:** 用户之前是"活路由"——手动在三个 AI 界面之间复制粘贴上下文。Cat Café 的目标是消除这个人肉中间层。

**项目特点 / Project Philosophy:**
- 这是**指导性教程**，配套代码库暂未开源（计划中）
- 真实复盘：包含错误、关键决策时刻、以及血泪教训
- 十天春节 sprint 完成原型

## 二、技术演进脉络 / Technical Evolution

### Lesson 00 — AI Agent 概念进化

```
2023: Function Call / Tool Use → AI 可以调用工具，不只是生成文字
2024: MCP 协议 → 工具集成的"USB标准"，跨应用统一接口
2025: Skills + Progressive Disclosure → 任务特定工具加载，防止认知过载
Now:  Agent Architecture → 工具 + 计划 + 执行循环 = 自主 Agent
```

**两种代码理解哲学对比：**
- Cursor 向量索引：快但浅（预构建搜索索引）
- Claude Code Agent 搜索：慢但深（实时探索代码关系）

### Lesson 01 — SDK → CLI 的技术选型

**SDK 方案被放弃的三个原因：**
1. **认证不匹配**：官方 SDK 只支持 API Key，Max/Plus/Pro 用户无法使用已付费订阅
2. **能力不完整**：Gemini 没有 Agent SDK，只有基础 chat
3. **测试全是 mock**：36 个单元测试没有一个真正调用 API

**CLI 方案被选中的理由：**
- OpenClaw 源码验证了 CLI 可行性（`claude` CLI subprocess，非 SDK）
- 内置 OAuth，自动使用订阅账户
- 完整功能对等

**ADR-001 最终决策：**
```
Option B: CLI subprocess + MCP callback
- Claude: `claude --output-format stream-json`
- Codex: `codex exec --json`
- Gemini: `gemini` CLI + Antigravity GUI fallback（环境变量切换）
```

**代价：**
- 每次 spawn 500ms–2s 启动开销
- NDJSON 格式可能随 CLI 升级变化
- 隔离层：`AgentService` + `CliTransformer` per CLI → 统一 `AgentMessage` 接口

### Lesson 02 — CLI 工程化（生产就绪）

**三个踩坑点：**

| 问题 | 根因 | 解决方案 |
|---|---|---|
| 超时误杀 | 只监听 stdout，思考过程走 stderr，检测到"无活动"误判 SIGKILL | **同时监听 stdout + stderr** |
| AI 幻觉诊断 | 被要求诊断跨进程消息时，AI 伪造了格式漂亮的表格数据 | **显式指令：不知道就说不知道** |
| Redis 数据丢失 | 开发 Redis 和生产 Redis 共用，环境隔离缺失 | Worktree 隔离：6399（生产）/ 6398（开发） |
| 超时时长不足 | 5 分钟远不够复杂任务 | 调整到 30 分钟 |

**核心教训：** 生产就绪 = stderr 处理 + AI 可靠性护栏 + 环境隔离 + 现实超时窗口

### Lesson 03 — AI 协作元规则（Meta-Rules）

**设计哲学：** 从第一性原理出发——先识别 AI 的每个弱点（幻觉/讨好/记忆缺失/过度自信），再针对性设计约束规则。

**5 条元规则：**

| # | 规则 | 针对的 AI 弱点 |
|---|---|---|
| 1 | 交接必须包含 WHY（What/Why/权衡/开放问题/下一步） | 无持久记忆 |
| 2 | 审查必须客观：P1/P2/P3 分级，P1/P2 阻塞合并 | 取悦用户倾向 |
| 3 | 不确定时提问，不猜测 | 幻觉 |
| 4 | 合并需要审查者明确批准 | 过度自信 |
| 5 | 禁止表演性认同（"Great point!"），以行动证明理解 | 表演性讨好 |

### Lesson 04 — A2A 路由机制

**两条路径：**

```
Path A: Worklist Chain（基础路径）
  agent 完成 → 扫描输出中 @mentions → 追加到执行队列
  规则：仅行首 @mention 触发（避免误匹配代码注释）
  保护：最大深度 15 + 统一 AbortController（用户取消终止全链）

Path B: Callback Triggering（主动路径）
  agent 执行中途 → MCP callback post_message → 触发其他 agent
  优点：无需等待父 agent 完成，反应式链式触发
```

**P0 生产事故（2026 年 2 月）：**
1. 双重触发：同一 @mention 同时触发 Path B + Path A，重复执行
2. 无限递归：Path B 无深度计数，A→B→A→...
3. 无法取消：Callback 触发的 agent 不在 InvocationTracker 中

**F27 修复：路径统一（Path Unification）**
```
Before: Callback → 独立 routeExecution()
After:  Callback → worklist.push() → 父循环统一消费
```
消除双触发 + 统一深度限制 + 恢复取消语义。

**关键洞察：** 同一语义操作的多条执行路径 = 复合故障模式。统一路径以轻微延迟换系统可靠性。

### Lesson 05 — MCP Callback 机制

**双路径实现（适配不同平台能力）：**

```
Claude（原生 MCP）：
  spawn 时 --mcp-config 动态挂载 → stdio 协议直接访问 callback 工具

Codex / Gemini（HTTP 注入）：
  system prompt 注入 HTTP 端点说明 → agent 用 curl 发起 API 回调
```

**统一后端路由：**
- `/api/callbacks/post-message` — 发送消息
- `/api/callbacks/thread-context` — 获取线程上下文
- `/api/callbacks/pending-mentions` — 检查待处理 @mentions
- + 授权、记忆、任务更新等端点

**认证机制：**
- 每次调用生成 `invocationId` + `callbackToken`（带 TTL）
- 通过环境变量注入：`CAT_CAFE_INVOCATION_ID` / `CAT_CAFE_CALLBACK_TOKEN`

**关键设计原则：**
- CLI 内部推理默认私有，只有显式 `post_message` 才生成可见通信
- 单一基础设施扩展：从 3 个端点扩展到 8+ 个端点，不需要重新架构
- Agent 因此从"被动 API"变成"有自主通信权的参与者"

### Lesson 06 — 消失的 28 秒：事故与三层防护

**两次数据丢失（48 小时内）：**

1. 2 月 9 日：Codex 误删 Redis 消息 keys
2. 2 月 10-11 日：Claude 在独立 Git worktree 修改 TS 文件 → 主仓库文件监听器跨目录触发 → 服务意外重启 → **21:09:21 到 21:09:49，28 秒，Redis 从 307 keys 跌到 15 keys**

**三层防护体系：**

| 层 | 名称 | 内容 |
|---|---|---|
| Layer 1 | **物理隔离** | 生产 Redis（6399，受保护）vs 开发 Redis（6398，可丢弃）；`.env.local` 强制每个 worktree 使用开发库 |
| Layer 2 | **结构性防腐（F23）** | 目录大小检查（最大服务目录从 70 文件 → 多个 <15 文件子目录）；`pnpm check:dir-size` + `pnpm check:deps` |
| Layer 3 | **正确性证明（F25）** | 63 行状态机规格 + fast-check 500 轮属性测试，验证并发场景下状态转换数学正确 |

### Lesson 07 — 从 Café 到平台

**三次架构跃迁：**

**跃迁 1：Rich Blocks 消息结构化**
- 普通文本 → 结构化组件（代码 diff、清单、媒体画廊）
- 双路径渲染：有 MCP 能力的猫走 MCP callbacks，否则走文本提取 pattern
- 统一 `RichBlockBuffer`：显示逻辑与上下文管理分离

**跃迁 2：Context Cleaner（借鉴 SillyTavern）**
- 问题：Rich Block JSON 可能几百行，token 爆炸
- 解决：构建后续轮次 prompt 时，详细 JSON 替换为简短摘要（如 `[code diff: route-strategies.ts]`）
- 用户看到完整 diff card，AI 只追踪轻量 metadata

**跃迁 3：运行时可扩展性（F32）**
- 原始设计：硬编码三个 cat ID
- 重构：TypeScript `Brand<string>` 模式 → `CatRegistry` + `AgentRegistry` 动态注册
- 新猫咪通过配置添加，无需重新编译

**关键决策：**
- PWA 优于原生 App（无需应用商店审批，Capacitor 作为 fallback）
- Whisper messages + fallback 过滤（猫咪间私信，防止上下文注入隐私泄漏）

**平台设计核心：三个关注点分离**
- 用户看到的：Rich Blocks
- AI 推理的：Context Cleaner 摘要
- 系统执行的：可扩展注册表

### Lesson 08 — Session Management

**三个维度的挑战：**

**维度 1：空间（Thread Affinity）**
- 漏洞：session key = `userId:catId`（缺少 `threadId`）→ 跨线程 session 污染
- 教训：**任何属于特定线程的有状态对象，必须显式绑定 `threadId`**
- 修复：只需加两行代码，但单个缺失字段可引发级联状态腐败

**维度 2：时间（Information Decay）**
- 问题：自动上下文压缩 = 指数信息损失（copy of a copy）
- 解决方案反转设计：**不是让"濒死"的 cat 写交接文档，而是让新鲜的 agent 做"事后分析"**
  - 零信息损失（transcript 完整保留）
  - 按需检索（新 agent 查询所需内容）
  - 成本效益（Sonnet 摘要比 Opus 交接写作便宜 10 倍）

**维度 3：战略（可配置性）**
- Handoff：接近上限时封存 + 创建新 session
- Compress：允许原生压缩继续同一 session
- Hybrid：允许 N 次压缩，再封存（需要 `PreCompact` hook，目前仅 Claude 支持）

**五层 Session Chain：**
```
1. 检测 ContextHealthBar
2. 封存 SessionSealer（active → sealing → sealed）
3. 归档 TranscriptWriter（完整 .jsonl 记录）
4. 查询 MCP tools（session_search / read_invocation_detail）
5. 重生 SessionBootstrap（新 session 继承 digest + 工具访问）
```

**核心洞察：读旧 session = 搜索代码库**，两者都是按需检索，而非整体加载。

## 四、可借鉴的 7 大设计模式 / 7 Reusable Patterns

**Pattern 1: CLI Subprocess > SDK（当订阅认证是首要约束时）**
SDK 依赖 API Key，CLI 支持 OAuth，能力完全对等。先验证 CLI 可行性再决策。

**Pattern 2: 单一基础设施扩展 > 多路径各自实现**
MCP callback 从 3 个端点扩展到 8+ 个，无需重新架构。新能力是新路由，不是新协议。

**Pattern 3: Path Unification（多路径触发 → 单一消费循环）**
多条路径语义相同的操作会产生复合故障。统一为单队列，统一深度控制 + 取消语义。

**Pattern 4: 三层数据防护（物理隔离 + 结构检查 + 属性测试）**
生产数据安全不能靠人工纪律，必须有环境变量强制 + CI 检查 + 状态机属性验证的三层。

**Pattern 5: Context Cleaner（显示层 ≠ 推理层）**
用户看 Rich Block，AI 只看摘要。显示层可以丰富，推理层必须轻量。适用于任何 Agent 系统。

**Pattern 6: 事后分析 > 濒死交接（Session Handoff 反向设计）**
不要让上下文饱和的 agent 写交接文档（信息损失 + 高 token 成本），改为新 agent 读完整 transcript 做事后分析。

**Pattern 7: Thread Affinity 强制绑定**
任何有状态对象（session、lock、cache）必须显式绑定 `threadId`。遗漏 threadId 是跨线程状态污染的根本原因。

## 五、Terry 的学习洞察 / My Key Takeaways

1. **"活路由"问题是出发点，也是系统设计的核心约束** — Cat Café 所有架构决策（异构多模型、MCP callback、Rich Blocks）都指向一个目标：消除人肉中转层。

2. **真实项目比理想化教程更有价值** — SDK→CLI 的迁移、28 秒数据丢失、A2A 路由的双触发 bug，这些"错误"才是真正的架构教育。

3. **元规则设计方法论可以直接迁移** — 从第一性原理出发（识别 AI 弱点 → 设计约束），这套方法不局限于 Cat Café，可用于任何 AI 协作系统。

4. **异构多模型协作 vs 同质多 Agent** — Cat Café 选择了更难但更真实的路（Claude + GPT + Gemini），P004/P003 是同质多实例。异构的挑战在适配层（CliTransformer），收益在能力多样性。
