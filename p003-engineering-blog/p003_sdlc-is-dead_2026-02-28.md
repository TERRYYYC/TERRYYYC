## 二、本次学习内容 / What I Studied Today

### 2.1 核心论点 / Core Argument

> "AI agents didn't make the SDLC faster. They killed it."
> "AI Agent 没有让 SDLC 变快——它们杀死了它。"

**"10x 开发者工具"的框架是错的。** 那个框架假设工作流不变，速度变快。现实是：整个生命周期正在内爆——阶段不是加速了，而是合并了。

The "10x developer tool" framing is wrong. It assumes the workflow stays the same, just faster. What's actually happening: the lifecycle is collapsing — stages didn't accelerate, they merged.

---

### 2.2 旧 SDLC vs 新循环的对比 / Old vs New

**旧 SDLC（宽循环 / Wide Loop）:**
```
需求 Requirements
    → 系统设计 System Design
    → 实现 Implementation
    → 测试 Testing
    → 代码审查 Code Review
    → 部署 Deployment
    → 监控 Monitoring
```
特征：离散、顺序、处处有交接（handoffs）、每个阶段有专属工具和仪式。

**新循环（紧循环 / Tight Loop）:**
```
意图 + 上下文 Intent + Context
    → AI Agent
    → 构建 + 测试 + 部署 Build + Test + Deploy
    → 观测 Observe
    → 下一个意图 Next Intent
```
特征：无工单、无 Sprint、无故事点、无 PR 队列、无独立 QA 阶段、无发布火车。**只有意图和执行 Agent。**

---

### 2.3 每个阶段的坍塌分析 / Stage-by-Stage Collapse

**① 需求阶段 → 迭代的副产品 / Requirements → Byproduct of Iteration**

需求曾经是被「下达」的——PM 写 PRD，工程师估点，冻结 spec。这在「实现昂贵」时有意义。现在当 Agent 能在分钟内生成完整功能版本时，你不再需要提前指定每个细节。你可以生成 10 个版本，选最好的那个。

Requirements used to be dictated — PM writes PRD, engineers estimate, spec gets frozen. That made sense when building was expensive. Now, when an agent generates a complete feature version in minutes, you generate 10 versions and pick the best one.

> **Jira 的命运：** Jira 被构建来追踪跨阶段的工作——而那些阶段已不存在。如果「需求」只是 Agent 的上下文输入，那 Jira 不再是项目管理工具，而是上下文存储。而且是一个糟糕的上下文存储。

**② 系统设计 → 被发现而非被指定 / System Design → Discovered, Not Dictated**

设计曾经在写代码之前完成——白板架构、辩论权衡、画方框和箭头。设计和代码之间的时间差以天或周计。

那个时间差正在关闭。设计变成了一件你通过给 Agent 正确上下文来「发现」的事，而不是你提前「指定」的事。模型见过的系统、架构、模式比任何单个工程师都多。当你描述问题时，Agent 不只是实现你的设计——它会建议往往优于你自己设计的架构。

设计仍然重要，但方式变了：你在实时协作设计，而不是提前规定设计。（工程师仍然需要知道 Agent 什么时候过度工程化或者遗漏了约束。）

**③ 实现 → Agent 的工作 / Implementation → Agent's Job**

显而易见。Agent 写代码，整个功能，包含完整的错误处理、类型、边界情况。作者不认识任何还在逐行打代码的人。我们审阅 Agent 写的内容，提供上下文，引导方向，专注于真正需要人类判断的问题。

**④ 测试 → 与实现同步，非顺序 / Testing → Simultaneous, Not Sequential**

Agent 在写代码的同时写测试，不是事后补，不是在单独的「测试阶段」。测试是生成的一部分。TDD 不再是一种方法论，这只是 Agent 默认的工作方式。独立的 QA 阶段消失了——没有「扔过墙给 QA」的交接。

**⑤ 代码审查 → 必须重新设计，PR 流程应该废弃 / Code Review → PR Flow Should Die**

> "The pull request flow needs to go... Clinging to the PR workflow in an agent-driven world isn't rigor. It's an identity crisis."
> "PR 工作流需要废弃……在 Agent 驱动的世界里坚守 PR 工作流不是严谨，是身份认同危机。"

逻辑：Agent 每天产生 500 个 PR，你的团队能审查 10 个。审查队列堆积。这不是值得优化的瓶颈，这是一个**假瓶颈**——只因为我们把人类仪式强加到机器工作流上才存在。

**应该变成什么样？**
```
Agent 生成代码
    → Agent 自我验证（对照 plan.md，运行测试，检查回归，验证架构约束）
    → 第二个 Agent 对抗性审查（试图在每个维度上破坏它）
    → 自动化检查（类型、安全扫描、行为差异）
    → 全通过 → 自动发布
    → 失败（可解决）→ Agent 修复
    → 失败（新颖问题）→ 人工介入
```
人类只在自动化验证无法解决冲突、或变更触及真正新颖的东西时才介入。

> "We're spending our review cycles reading diffs that an agent could verify in seconds. That's not quality assurance. That's luddism."
> "我们把审查周期花在阅读 diff 上——而 Agent 可以在秒内完成这件事。这不是质量保障，这是勒德主义（现代版反技术进步）。"

**⑥ 部署 → 解耦与持续 / Deployment → Decoupled and Continuous**

Agent 写的部署流水线比大多数团队手工构建的更精细：feature flags、金丝雀发布、渐进式推送、自动回滚触发器——以前需要专属平台团队的那种发布工程。

关键转变：Agent 自然地把**部署（deploy）** 和**发布（release）** 解耦。代码持续部署，每次变更在生成并验证后立即落到生产环境的 flag 后面。发布是一个独立决策，由 feature flags 或流量规则驱动。

**未来更进一步：** Agent 不只是部署代码，还管理整个发布生命周期——监控推出进度、根据错误率调整流量百分比、延迟峰值时自动回滚，只有在真正新颖的问题发生时才通知人类。

**⑦ 监控 → 唯一幸存的阶段，但必须进化 / Monitoring → Last Stage Standing, Must Evolve**

监控是 SDLC 中唯一幸存的阶段。不只是幸存——它变成了整个系统赖以为基础的根基。

当 Agent 比人类能审查的速度更快地发布代码时，可观测性不再是「锦上添花的仪表盘层」，而是整个坍塌生命周期的**主要安全机制**。设计审查、代码审查、QA 阶段、发布签字——都被吸收或消除了。监控是剩下的一切。

**问题：** 大多数可观测性平台是为人类构建的——告警、日志搜索、仪表盘，都为人去看、理解、行动而设计。当变更量超过人类注意力时，这个模型崩溃。500 次变更/天 + 每次异常需要人工调查 = 只是把瓶颈从代码审查移到了事故响应。

**应该变成什么样？**
```
遥测数据（observability）
    → 成为发布了这段代码的 Agent 的上下文输入
    → Agent 自动检测回归
    → Agent 自动修复
    → 进入下一个意图
```
可观测性层变成驱动整个循环的反馈机制——不是末尾的一个阶段，而是整个系统的结缔组织。

> "Observability without action is just expensive storage."
> "没有行动的可观测性只是昂贵的存储。"

---

### 2.4 最终结论 / Conclusion

> **"The SDLC is dead. The new skill is context engineering. The new safety net is observability."**
> **"SDLC 已死。新技能是上下文工程。新安全网是可观测性。"**

**上下文工程（Context Engineering）** — 你构建出的东西的质量，直接正比于你给 Agent 的上下文质量。不是流程，不是仪式——是上下文。

## 三、洞察与收获 / Insights & Takeaways

### 3.1 最重要的 3 个发现 / Top 3 Insights

1. **"AI-native 工程师不知道 SDLC 是什么，而且这没问题"** ——在 Cursor 发布后开始职业生涯的工程师，从未经历过 Sprint 规划、故事点估算、等待三天 PR 审查。他们没有被仪式束缚。他们直接去构建东西了。这不是缺陷，是优势。

   AI-native engineers who started after Cursor launched never sat through sprint planning, estimated story points, or waited 3 days for a PR review. They're unencumbered by ceremony. They just build things. This isn't a deficit — it's an advantage.

2. **监控从「仪表盘层」进化为「整个系统的结缔组织」** ——当所有其他安全机制被吸收或消除后，可观测性成为最后一道防线。但大多数可观测性平台仍为人类设计。真正的进化是：遥测数据直接成为 Agent 的上下文输入，形成自修复的闭环系统。

   Monitoring evolves from "nice-to-have dashboarding layer" to "connective tissue of the entire system." The future is observability that feeds directly back into the agent loop — closed-loop, self-correcting, not just expensive storage.

3. **代码审查执着于 PR 是"勒德主义"，不是严谨** ——这个观点极具挑战性，但论证有力：当 Agent 能在秒内验证 diff 时，让人类花时间阅读 diff 不是质量保障，是把人类仪式强加到机器工作流上。真正的解决方案是 Agent 自我验证 + 对抗性第二 Agent 审查。

   Clinging to PR review in an agent-driven world is "luddism." Real quality assurance is: agent self-verification + adversarial second agent review + automated checks — humans only for genuinely novel problems.

### 3.2 让我意外的地方 / What Surprised Me

- **Jira 的重新定位**——作者指出 Jira 如今应该被理解为「上下文存储」（context store），而不是项目管理工具——但它是一个糟糕的上下文存储，因为它不是为 Agent 消费而设计的。这是一个尖锐的观察：工具的设计假设改变了，但工具本身没变。

  Jira reframed as a "context store" — but a terrible one, since it wasn't designed for agent consumption. The design assumptions of our tools have changed, but the tools haven't.

- **设计的去中心化**——系统设计现在通过给 Agent 正确上下文来「发现」，而不是在写代码前「规定」。模型见过比任何个人更多的系统和架构模式，往往能建议更好的架构。这意味着工程师角色从「架构规定者」转变为「约束守护者」。

  System design is now "discovered" through giving agents the right context, not "dictated" upfront. Engineers shift from "architecture prescribers" to "constraint guardians."

## 四、挑战性观点的审视 / Skeptical Review

> 我持怀疑态度，所以对文章中最激进的观点做一个审视：

**观点 1："PR 流程必须废弃"**

这个论点在高速 AI 代码生成场景下有力，但前提假设存疑：
- 文章假设 Agent 自我验证 + 对抗性 Agent 审查能等效替代人类审查——这在当前 Agent 可靠性水平下尚未成立，特别是对业务逻辑正确性的验证
- 「500 PRs/day」的规模更适用于纯 AI 驱动的大规模代码生成场景，对于多数中小型团队，PR 流程的社会功能（知识共享、代码标准传播）价值仍不可忽视
- **更准确的结论可能是**：PR 必须从「全量人工审查」转向「例外-based 人工审查」，而不是完全废弃

**观点 2："没有人再逐行打代码了"**

这是经验性陈述，具有选择性偏差——作者的圈子可能集中于 AI-heavy 工程团队。在嵌入式系统、底层内核开发、高安全认证领域，手工编码仍然必要。

**核心观点仍然成立：** SDLC 阶段在 AI 辅助场景下确实正在合并，这个宏观趋势是准确的。激进程度可以商榷，方向不容否认。
